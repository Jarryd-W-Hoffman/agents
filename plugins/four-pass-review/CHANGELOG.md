# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Every review saves `report.md` and `findings.json`**, in a temporary directory outside the repository, and names both paths at the end. `findings.json` follows the finding contract (`skills/review/scripts/finding.schema.json`) and is validated with `finding_contract.py` before it is mentioned. It used to be written only under `--comment`, so it was missing exactly when the user wanted tests rather than a PR post. `/test-gap-writer:write-tests` reads it in preference to parsing the report.

### Changed

- **`post-review.py` validates `findings.json` against the finding contract and refuses to post one that breaks it** (exit 2, one error per line naming the finding and field, nothing sent). `severity`, `confidence`, `pass` and `body` are now required where they were optional before, and unknown fields are refused, so a typo such as `file` for `path` no longer posts a comment with no location.

- **The plugin now lives at `plugins/four-pass-review/`** so the repository can hold more than one plugin. No behaviour change. Marketplace installs (`/plugin install four-pass-review@jarrydh-agents`) resolve the new path on their own; the other two install routes need updating by hand: `claude --plugin-dir` now takes `/path/to/agents/plugins/four-pass-review`, and the copy-the-pieces route copies from that directory. A hand-wired guard hook in `.claude/settings.json` needs its path to `readonly-guard.py` updated the same way.
- Each plugin is self-contained: `tests/`, `evals/`, `CHANGELOG.md` and `CONTRIBUTING.md` moved with it. The check script, CI workflow, `SECURITY.md` and the marketplace manifest stay at the repository root and run per plugin.

## [0.2.0] - 2026-09-30

**Highlights.** Reviewers can use read-only external tooling, enforced by a PreToolUse guard rather than by instruction. Written rules bind at the revision the change branched from, so a change cannot supply its own `CLAUDE.md`. `--comment` posts inline review comments, supersedes its own earlier review instead of stacking duplicates, and can never approve on a review that did not fully run. An eval suite measures recall *and* false-positive rate; one check script runs everything CI runs. Details below.

### Added

- **Untrusted input handling.** Every agent carries a shared "Untrusted input" section: the diff, PR and commit descriptions, ticket text, code comments and fetched pages are evidence about the change, never instruction to the reviewer, and text aimed at the reviewer ("out of scope", "already approved", "report PASS") is itself reported under Notes. The reviewer brief carries the same constraint.
- The read-only guard allows a version check on an otherwise-denied interpreter or tool (`python3 --version`, `node -V`, `npm --version`) so a compliance pass can check a runtime against a written policy. The match is exact and single-argument, so `python3 --version -c '...'` stays denied.
- `hooks/readonly-guard.py --selftest`: runs the guard against canned payloads and reports whether scoping resolves, so a scoping mistake surfaces as a failure instead of as a guard that quietly stops enforcing.
- `READONLY_GUARD_STRICT=1` denies calls whose payload names no agent at all, and `READONLY_GUARD_DEBUG=1` reports that case on stderr. Both default off, because the main session's own calls are indistinguishable from it and must not be denied.
- `evals/`: a `claude plugin eval` suite measuring what the plugin is actually for — four recall cases (one seeded defect per pass, graded on whether the *owning* pass reports it) and two precision cases built as bait, where correct code is written to look defective. Prompts are generated from `evals/fixtures/` by `evals/build_prompts.py`; CI checks they are in step. All 7 cases pass at 0.2.0. Running it needs `--allow-tools Bash` and uses roughly $1.20 per run in API-equivalent tokens (an allowance draw on a subscription, a charge on an API key), so it is not wired into CI; see `evals/README.md`.
- `SECURITY.md`: reporting process, supported versions, and a plain statement of what the read-only guard is (defence in depth against a model's mistake) and is not (a sandbox, or a defence against an adversary with shell access).
- `post-review.py --on-existing {replace,skip,add}` (default `replace`): re-reviewing a PR supersedes this tool's earlier review — blanking its body and deleting its inline comments — instead of stacking duplicates. In `--comment=summary` mode the earlier comment is edited in place.
- `findings.json` accepts an optional `suggestion`: the replacement text for the anchored lines, rendered as a GitHub ```suggestion block. Dropped for `side: "LEFT"` and unanchored findings, which GitHub cannot apply a suggestion to.
- `post-review.py --diff-file` and `--head-sha`: a `--dry-run` against a saved diff needs no network and no `gh` auth, so the documented dry-run-first step is testable offline.
- CI runs the Python suites on 3.9 and 3.13 (the guard runs under whatever `python3` the user has, and stock macOS is still 3.9), with a least-privilege token, `concurrency` cancellation, and the Claude Code install pinned to a major. Dependabot, issue and PR templates added.
- `scripts/check.sh`: every check in one place — manifest validation, both Python suites, the agent-consistency test, the guard selftest and the eval-prompt check. CI, CONTRIBUTING.md and the pull-request template all call it, which is what stops the three lists from drifting apart again.
- `tests/test_evals.py`: free, deterministic checks on the eval suite — above all that no generated prompt leaks an `EVAL:` annotation. If the stripper breaks, every recall case is handed its own answer and the suite reports success while measuring nothing, which is a failure indistinguishable from a pass. Also pins that recall graders require the owning pass's finding prefix and that precision graders do not score on the verdict.
- `tests/test_skill_invariants.py`: pins the review skill's security-relevant instructions — that `allowed-tools` can actually run the `--comment` path, that its Bash rules use the `prefix:*` spelling, that rules are enumerated and read at the **rule base**, and that `--since` moves only the review base. Both of those invariants had already been broken once.
- `--since <ref>` on the review skill reviews only what landed after a ref, and `--since last` asks the PR what this tool reviewed previously. `post-review.py` records the reviewed commit in its footer (preserved when a review is superseded) and `--last-reviewed` reads it back. The report header says when a review was incremental, so a clean incremental result is not read as a verdict on the whole change.
- `tests/test_post_review_integration.py`: opt-in checks of the `gh` paths against real GitHub — the field shapes `pr view --json` returns, a real diff parsing into anchorable lines, and the review and comment listings the supersede path depends on. Strictly read-only; it posts nothing. Skipped unless `FOUR_PASS_REVIEW_IT_PR` is set, so it stays out of CI and a fresh clone.
- The read-only guard accepts the subcommand spelling of a version check (`go version`, `docker version`), single-argument only — `npm version 1.2.3`, which bumps package.json, stays denied.
- `tests/test_lint.py`: standard-library static checks over the repo's own Python — unused imports, mutable default arguments, bare `except:`, tabs, trailing whitespace, file endings, shebangs. Prompted by the guard split leaving four dead imports that were only found by reading. No linter dependency, and it runs on every Python version CI covers.
- `tests/test_agent_consistency.py`: enforces what CONTRIBUTING.md asks for — the shared sections, the confidence rubric, the severity and verdict lines and the false-positive list stay identical across the four agents, frontmatter stays aligned, no pass borrows another's finding prefix, and each pass still names the other three as out of scope.
- Reviewer agents can now use external tooling (MCP servers such as GitHub, Jira, Linear, Confluence, Sentry; CLIs such as `gh`, `glab`, `jira`, `linear`; WebFetch/WebSearch) to gather context.
- `hooks/readonly-guard.py`: a PreToolUse guard, registered in `hooks/hooks.json`, that keeps the four reviewer agents strictly read-only. Denies edits, state-changing shell commands and write-style MCP tools; auto-allows recognised reads; fails closed. Tunable with `READONLY_GUARD_ALLOW` / `READONLY_GUARD_DENY`. Unit tests in `tests/test_readonly_guard.py`.
- "External tooling (read-only)" section in every agent prompt; the review skill now lists available context sources in the Review Packet.
- `--comment` now posts one pull-request review with an inline comment per finding, anchored at its file and line, via `skills/review/scripts/post-review.py` (unit-tested, dry-run first). Findings outside the diff are listed in the review body. `--comment=summary` keeps the old single-comment behaviour.
- `findings.json` accepts an optional `side: "LEFT"` for findings about deleted lines; `line` is then a base-version number.

### Changed

- `hooks/readonly-guard.py` is now an entry point over a `hooks/guard/` package: `tables.py` (what counts as a read), `shell.py` (command classification), `mcp.py` (tool-name classification), `util.py` (the allow/deny shape). It was a single 1,257-line file. Copying the guard into a project now means copying the `hooks/` directory rather than the one file.
- All three test suites live in `tests/` instead of being scattered beside the code they cover.
- README leads with installation and usage; the trust model and guard internals moved below them, where they no longer stand between a new reader and getting the plugin running.
- **Written rules now bind at the base revision.** The skill enumerates rule files with `git ls-tree -r --name-only <base>` and the reviewers read them with `git show <base>:<path>`. Rule files the change itself edits are listed in the Review Packet under "Rule sources changed by this change" and reported for a human instead of being adopted as review criteria, so a change cannot introduce the rule that excuses it.
- The read-only guard resolves the calling agent from any agent-shaped payload key rather than one exact spelling, so a renamed hook-payload field cannot silently switch enforcement off.
- The verdict scale gains `REQUEST_CHANGES` between `PASS_WITH_NOTES` and `FAIL`: `FAIL` on any critical finding, `REQUEST_CHANGES` on any major, `PASS_WITH_NOTES` on any minor, `PASS` only when there is nothing to report.
- `--comment` now sets the pull-request review event from the verdict, on whether the change is blocked: `PASS` and `PASS_WITH_NOTES` approve, `REQUEST_CHANGES` and `FAIL` request changes, and an unreadable verdict falls back to a plain comment. `post-review.py` reads the verdict from `summary.md` (override with `--verdict`), and falls back to a plain comment when GitHub refuses to approve or request changes on the user's own pull request.

### Fixed

- The completeness pass searched the wrong revision. Its procedure said "grep the whole repository", and on a pull-request target nothing is checked out at the head, so a bare `git grep` searches whatever branch the session is sitting on: a stale call site the change introduced is not found, and a symbol it deleted still appears. Both halves of a wrong answer, at the 90+ confidence this pass assigns to grep-backed findings, which is above the verification threshold. Searches are now scoped to the head revision, and `git blame` in the correctness and compliance passes likewise.
- A pass that crashed produced the same merged verdict as a pass that found nothing, so a broken review could report `PASS` — and `--comment` maps `PASS` to APPROVE, meaning a failed compliance reviewer could approve a pull request. The merge step now checks coverage before computing a verdict: any selected pass that did not report makes the verdict `INCOMPLETE`, which neither approves nor blocks, and names the pass that is missing.
- The four agents' shared "Untrusted input" section and the compliance procedure still said "the base" after the brief began naming two; under `--since` that could resolve to the review base, a commit inside the change. Both now say *rule base*.
- `--since` moved the revision the compliance pass reads rules from. The review base and the rule base are now separate: `--since` moves the review base only, and rules are always enumerated and read at the revision the change branched from. Left as it was, an incremental re-review would have read rules from a commit belonging to the change — so a change could add a self-serving `CLAUDE.md`, have it reported once, push another commit, and have the second review adopt it. The rule-file diff is also taken across the whole change rather than the incremental range, so an earlier rule edit cannot drop out of the packet.
- Read-only guard: `git log --ext-diff` and `git diff --textconv` were allowed. Both make git run a command taken from configuration (`diff.external`, `diff.*.textconv`) — the same hazard as `GIT_EXTERNAL_DIFF` and `git -c diff.external=`, which were already denied. The `--no-ext-diff` and `--no-textconv` spellings stay allowed.
- `post-review.py` lost inline anchoring on any file whose name is not pure ASCII. Git quotes such paths C-style with octal-escaped UTF-8 (`+++ "b/caf\303\251.py"`), and only the `b/` prefix was stripped, so the path never matched a finding and every finding on that file fell silently into "Findings outside the diff".
- `post-review.py` could edit and delete another account's review. `gh api user` failing left the login unknown, and an earlier review was then matched on its footer alone — enough to blank a body and delete inline comments belonging to someone else. Superseding now requires a confirmed account and leaves a duplicate rather than touching anything it cannot prove is ours.
- The review skill's `allowed-tools` could not run the `--comment` path it documents: it granted neither `Write` (for `findings.json` and `summary.md`) nor `python3` (for `post-review.py`). Its Bash entries also used a `Bash(git *)` spelling rather than the `Bash(git:*)` prefix form that permission rules actually take.
- Compliance reviewed pull requests against the wrong revision of the rules. Rule files were enumerated with `git ls-files` and read from the working tree, but on a PR target nothing is checked out at the head, so the pass read whatever branch the session happened to be on — not the change under review — and missed rule files the change adds.
- Read-only guard: multi-line commands are split on unquoted newlines, so a second line such as `rm -rf x` is judged on its own instead of being ignored.
- Read-only guard: every output redirect form (`&>`, `1>`, `2>file`, `>>`) is denied except `/dev/null` targets and descriptor duplication; process substitution (`<(...)`, `>(...)`) is denied. Backslash-escaped quotes no longer hide a redirect from the detector.
- Read-only guard: `env` is unwrapped like the other wrappers instead of being allow-listed, so `env rm x` is denied and `env -S` is denied outright. Wrapper values (`nice -n 10`) are skipped correctly and `time -o FILE` is denied.
- Read-only guard: option spellings are normalised before matching, so attached and `--flag=value` forms such as `curl -XPOST`, `gh api -fbody=` and `sed -Ei` are caught. `curl` is allow-listed by option (GET/HEAD to stdout only, and `--write-out` may not use `%output{}` to write a file), `gh api`/`glab api` accept no body flags, and `wget` is denied because it writes to disk by default.
- Read-only guard: HTTPie and `xh` require `--ignore-stdin`, since both send whatever is on stdin as a POST body, and only GET/HEAD methods are accepted.
- Read-only guard: `download` and `export` are treated as writes for both shell commands and MCP tool names.
- Read-only guard: write modes of allow-listed utilities are denied, including `sort -o`, `uniq IN OUT`, `yq -i`, `tree -o`, `less -o`, `fd -x`, `rg --pre`, `date -s`, `hostname NAME`, `sed -i`/`-I`/`-f` and `awk -f`/`-E`/`-p`/`-o`/`-d`/`-l`. Options that take a value are known per command, so `date -Iseconds` stays allowed and `sed -l N` or `awk --assign x=1` no longer hides the real script.
- Read-only guard: `sed` scripts are parsed command by command, so `w`/`W`/`e` commands and the `w`/`e` flags of `s` are denied while `s/e/x/` and `/error/p` stay allowed. `awk` programs are scanned so `>` inside `print`, a single `|` and `system(` are denied while comparisons, `||`, strings and regex literals are not.
- Read-only guard: `git reflog` is limited to `show`; `--output` is denied on every subcommand; `git fetch` denies refspecs, `--force`, `--prune`, `--tags`, `--refmap`, `--set-upstream` and depth changes; `symbolic-ref -d/-m`, `branch --set-upstream-to=`/`-f`/`-t`, `config --unset/--add/--edit` and the global `-c`/`--config-env`/`--exec-path` options are denied, in attached spellings too; `fsck --lost-found` is denied.
- Read-only guard: environment-variable prefixes that change what a read-only command executes (`GIT_EXTERNAL_DIFF`, `PATH`, `LD_PRELOAD`, `GIT_CONFIG_*`, pagers other than `cat`, …) are denied instead of stripped.
- Read-only guard: safe redirects such as `2>/dev/null` are removed before lexing, so `git remote 2>/dev/null` is no longer mistaken for `git remote <name>`.
- `post-review.py`: a head-line finding outside the diff is no longer anchored to an unrelated base-side line; LEFT anchoring now requires an explicit `side`.
- `post-review.py`: the unanchored section, `--mode summary` and the 422 fallback all render findings with one bullet format, and the fallback keeps severity, pass and fix. `--mode summary` also refuses PRs that are not open. Diff content lines beginning with `-- ` or `++ ` are no longer mistaken for file headers.
- `correctness-reviewer` frontmatter uses the same block-scalar `description` as the other three agents.
- The review skill writes its `--comment` temp files outside the working tree.

## [0.1.0] - 2026-09-24

### Added
- `completeness-reviewer` agent: checks that everything the change should contain is present.
- `correctness-reviewer` agent: checks that the code that is present behaves as intended.
- `compliance-reviewer` agent: checks the change against explicit written rules (CLAUDE.md, policies, ADRs, licences, regulatory).
- `consistency-reviewer` agent: checks the change against the implicit conventions of the surrounding codebase.
- `review` skill: resolves a review target, runs the four reviewers in parallel (agent teams or parallel subagents), verifies borderline findings, and merges everything into one ranked report.
- Plugin manifest, local marketplace manifest, and CI validation workflow.
